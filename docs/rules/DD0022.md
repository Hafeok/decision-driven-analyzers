# DD0022: Declare the namespace the file's folder names

|  |  |
| --- | --- |
| **Id** | `DD0022` |
| **Tier** | 1 (error, mechanical, single compilation) |
| **Severity** | error |
| **Motivating decision** | `NamesAndNamespaces.NamespaceMatchesFolder` |
| **Introduced in** | 0.1.0-preview.12 |

## Principle

A namespace is a claim about where a type lives, and the folder is where a reader looks for it. A
reader who browses the tree and a reader who follows a namespace should arrive at the same file;
when they do not, the structure the namespaces describe is not the structure the repository has.

## What the rule checks

The expected namespace of a file is the **root namespace** followed by the file's **folder path
relative to the project directory**, one segment per folder, joined with `.`. The root is the
`RootNamespace` MSBuild property when it is set and non-empty, otherwise the assembly name. The
comparison is ordinal and case-sensitive; separators are normalised, so Windows and Linux paths
compare the same.

Three things are reported:

- **A namespace declaration whose full name is not the expected name**, block or file-scoped, at
  the name. A block nested in another is checked by its full name, `Outer.Inner`. A block that holds
  only nested blocks and no types of its own is not itself reported: every type ends up in some
  innermost declaration, and that one is checked.
- **A type in the global namespace**, at its identifier: a class, struct, interface, enum, record
  or delegate declared outside any namespace.
- **A folder whose name is not a valid C# identifier**, once per file, at the first namespace name
  or type identifier. No namespace can name `my-stuff` or `2024`, so the file is reported for the
  folder rather than for whichever namespace it happens to declare.

Two things are not checked, by `NamesAndNamespaces.NamespaceMatchesFolder`:

- **Generated code** (`RuleTiers.GeneratedCodeIsExempt`): a generator's output, `*.g.cs`,
  `*.generated.cs`, `*.designer.cs`, and files in the intermediate output directory, where the SDK
  writes `AssemblyInfo.cs`.
- **Files outside the project directory**: a linked file belongs to another project's structure.

## Configuration

| Setting | Where | Default | Effect |
| --- | --- | --- | --- |
| `ProjectDir` | MSBuild, set by the SDK | the project file's directory | The directory folders are relative to. The rule runs only when it is present. |
| `RootNamespace` | MSBuild, set by the SDK | the project name | The first segment(s) of every expected namespace. Empty means unset, and the assembly name is used. |
| `dotnet_diagnostic.DD0022.severity` | `.editorconfig` | `error` (tier 1) | Downgrading it below `error` is DD0008. |

Both properties are compiler-visible in every SDK project without anything from this package.
**With no `ProjectDir` the rule is silent**: there is nothing to compare a path against. A build
through an SDK project always has one; a compilation driven some other way may not, and then the
rule reports nothing rather than guessing.

## False-positive story

Tier 1 and decidable: a string built from a path, compared with a string the compiler bound. The
edge cases are the ones the decision names, and each is a ruling rather than a guess:

- **A file at the project root** expects exactly the root namespace.
- **A folder that is not an identifier** is reported as such, not as a namespace mismatch.
- **Case** matters: `Ingest/` expects `Ingest`, not `ingest`.
- **A `RootNamespace` that differs from the assembly name** is honoured, because it is what the
  SDK's own templates generate namespaces from.

The honest exception is a migration in progress: a tree whose files are being moved one folder at a
time, where a declaration is right and the file has not caught up yet. That is
`[DesignDecision(..., Scope = ExceptionScope.Migration)]` on **every type declared directly in the
offending namespace declaration**, citing the decision that says the move is under way. A
declaration where only some of its types carry it is still reported: it still holds a type nobody
decided about.

IDE0130 checks the same thing in an IDE and is not the answer here (ADR-A17): it runs in a build
only with `EnforceCodeStyleInBuild=true`, which this package cannot set for a consumer without
switching on every IDE rule, and its severity can be lowered in `.editorconfig`, which is a
suppression path DD0008 cannot see.

Suppressing the diagnostic is not an answer (that is DD0008).

## Applying the fixes

`dotnet build` never runs a code fix, so a fix that only an IDE can reach is invisible to anyone
working from a terminal — an agent included. From a terminal:

```
dotnet format analyzers --diagnostics DD0022
```

The design-change fix **declares the namespace the folder names**: it rewrites the declaration's
name, and for a nested block only the block's own part, when the expected name lies under the
containing block. Moving the file is not a code fix: a code action edits documents, and a move is a
change to the project tree that the IDE's own rename does with the references updated. A type in
the global namespace gets no fix, because wrapping it in a declaration is a decision about which of
the file's members belong together. There is no fix-all: each rename changes what every other file
that used the old name has to import.

The documented-exception path is `[DesignDecision]` on every type in the declaration, which a
declaration cannot carry itself, so the shared placeholder fix is not offered for this rule.

## Violating example

```csharp
// Sample.Layer1/Ingest/Reader.cs, in project Sample.Layer1
namespace Sample.Layer1
{
    public sealed class Reader { }
}
```

```text
DD0022: namespace 'Sample.Layer1' is declared in 'Ingest/Reader.cs', whose folder names 'Sample.Layer1.Ingest'.
Decide: declare 'Sample.Layer1.Ingest', or move the file to the folder 'Sample.Layer1' names | mark it [DesignDecision(typeof(<Set>.<Key>), Scope = ExceptionScope.<Scope>)] citing the accepted decision that says so.
Do not add the attribute without a decision that answers this; if the reason is only that the code already looked like this, take the design change.
```

## Conforming example

```csharp
// Sample.Layer1/Ingest/Reader.cs, in project Sample.Layer1
namespace Sample.Layer1.Ingest;

public sealed class Reader { }
```

A single-namespace assembly conforms too: every file at the project root declares the root
namespace, and `NamesAndNamespaces.NamespaceDepthNotRequired` says no rule asks for more.
