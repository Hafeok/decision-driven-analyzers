# DD0011: Contract parameters are data, not collaborators

|  |  |
| --- | --- |
| **Id** | `DD0011` |
| **Tier** | 1 (error, mechanical, single compilation) |
| **Severity** | error |
| **Motivating decision** | `Contracts.DataVersusCollaboratorParameters` |
| **Introduced in** | unreleased |

## Principle

A collaborator handed in per call is a dependency every caller has to satisfy at every call site,
and one the compiler cannot place in any layer, because it has no idea what will be handed in.

## What the rule checks

Parameters of `[Contract]` members, and two findings:

- **An interface or abstract-class parameter that no decision declares a contract.** An array of
  them counts: that is a collaborator with a loop around it.
- **An `object` parameter.** The same move with the type name taken off.

Everything else is data and is not this rule's business: delegates, enums, structs, type parameters,
spans and memories, `CancellationToken`, and anything `[Contract]`-marked.

**BCL interfaces are data.** `IEnumerable<T>` and its relatives are how the framework spells a
sequence. ADR-A08 allows "a model type (from the allowed vocabulary)" and then disallows interfaces;
read in that order the second clause never reaches a framework type, and read the other way round
the rule would report every sequence parameter in every contract. The line is where the ADR draws it
in prose: a collaborator is the thing a consumer would otherwise have injected.

Return types are not checked here. A returned interface is DD0010's question about which package it
comes from; this rule is about what a caller has to supply.

## Configuration

| Setting | Where | Default | Effect |
| --- | --- | --- | --- |
| `ArchLayer` | MSBuild property | none | The rule runs only when this is set. |
| `ArchCompositionRoot` | MSBuild property | `false` | `true` excludes the project. |
| `dotnet_diagnostic.DD0011.severity` | `.editorconfig` | `error` (tier 1) | Downgrading it below `error` is DD0008. |

Nothing else. There is no list of allowed collaborator types, because the point of the rule is that
there is no such list: a collaborator that a contract is allowed to take is one somebody declared a
contract.

## False-positive story

Tier 1 and decidable: the parameter's type kind, its attributes, and its assembly.

The case that looks like a false positive and is not: a visitor or a callback expressed as an
interface. `void Accept(IVisitor visitor)` is reported, and the honest answers are to make it a
delegate, which is what it is, or to declare `IVisitor` a contract, which says that passing it is
intended. Both are better than the third option, which is that nobody ever decided.

The BCL carve-out above is a reading of two clauses in ADR-A08 that do not order themselves. It is
recorded here rather than left in the analyzer, because a consumer who disagrees needs to be able to
point at the sentence.

## Applying the fixes

`dotnet build` never runs a code fix, so a fix that only an IDE can reach is invisible to anyone
working from a terminal — an agent included. From a terminal:

```
dotnet format analyzers --diagnostics DD0011
```

No fix is registered. Moving a parameter to a constructor changes every implementer and every call
site, and marking the parameter's type a contract needs a decision key. A code action that did
either silently would be a refactor disguised as a lightbulb.

## Violating example

```csharp
namespace Consumer
{
    [Contract(typeof(CatalogShape.ProductLookupContract), Role = "catalog read side")]
    public interface IProductLookup
    {
        Product? Find(ProductId id, IClock clock);
    }

    public interface IClock { }
}
```

```text
DD0011: parameter 'clock' of contract member 'IProductLookup.Find' is 'Consumer.IClock', an interface no decision declares a contract.
Decide: take it through the constructor of the implementing type, or mark 'Consumer.IClock' [Contract(typeof(<Set>.<Key>), Role = "...")] so that passing it is a declared dependency | mark it [DesignDecision(typeof(<Set>.<Key>), Scope = ExceptionScope.<Scope>)] citing the accepted decision that says so.
Do not add the attribute without a decision that answers this; if the reason is only that the code already looked like this, take the design change.
```

## Conforming example

```csharp
namespace Consumer
{
    [Contract(typeof(CatalogShape.ProductLookupContract), Role = "catalog read side")]
    public interface IProductLookup
    {
        Product? Find(ProductId id, DateTimeOffset asOf);
    }
}
```

The clock was never the caller's business: what the member needs is the instant, which is data.
