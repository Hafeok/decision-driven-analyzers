# DD0003: Do not resolve services outside the composition root

|  |  |
| --- | --- |
| **Id** | `DD0003` |
| **Tier** | 1 (error, mechanical, single compilation) |
| **Severity** | error |
| **Motivating decision** | `StableDependencyRules.NoServiceLocationOutsideCompositionRoot` |
| **Introduced in** | unreleased |

## Principle

A dependency taken as a constructor parameter is checked by the compiler and visible in the
reference graph. The same dependency pulled from a container is checked at run time and visible to
nobody.

## What the rule checks

Outside a composition root, these calls are errors:

| Call | Matched by |
| --- | --- |
| `IServiceProvider.GetService` | the interface method itself |
| `GetService`, `GetRequiredService`, `GetKeyedService`, `GetRequiredKeyedService`, `GetServices`, `GetKeyedServices` | an extension method whose receiver is `System.IServiceProvider` |
| `ActivatorUtilities.*` | the type name plus the `Microsoft.Extensions.DependencyInjection` namespace |
| `Activator.CreateInstance` | `System.Activator` |

Matched on names and receiver types rather than on symbol identity, so that a consumer's own
extension over `IServiceProvider` counts as service location too — it is the same act. The receiver
is what decides: a method called `GetService` on an unrelated type is not reported.

## Configuration

| Setting | Where | Default | Effect |
| --- | --- | --- | --- |
| `ArchCompositionRoot` | MSBuild property | `false` | When `true`, the rule registers nothing at all in that project |

The composition root is the one project whose job is wiring, and it says so with a property rather
than by suppressing the rule — a suppression would hide the same call everywhere else too.

## False-positive story

Tier 1, but the one of the three with a real false-positive surface: these method names are common.
`GetService` on a catalogue, a registry or a domain type is ordinary code, and the rule must not
report it. It does not, because the receiver decides rather than the verb — the test for this is
`A_method_named_GetService_on_an_unrelated_type_is_not_reported`.

The remaining case is a project that genuinely does some wiring without being *the* composition
root — a plugin host, say. Setting `ArchCompositionRoot=true` there is the honest answer if it
really is one; if it is not, the exception path is `[DesignDecision(...)]` on the member that
resolves, citing the decision that says so. Suppression is DD0008.

## Applying the fixes

`dotnet build` never runs a code fix, so a fix that only an IDE can reach is invisible to anyone
working from a terminal — an agent included. From a terminal:

```
dotnet format analyzers --diagnostics DD0003
```

One fix: the documented-exception placeholder, on the member that resolves.

There is no mechanical design change here. Replacing a resolution with a constructor parameter means
deciding what that parameter is and who supplies it, which is the work the rule exists to make
somebody do.

The documented-exception fix inserts `[DesignDecision(typeof(____.____), Scope = ExceptionScope.____)]`,
which does not compile (`DiagnosticMessages.PlaceholderFixDoesNotCompile`). That is the point: the
build stays red with one remaining error naming exactly what is missing, and no fix reaches green
without either a design change or a filed, accepted decision.

## Violating example

```csharp
internal sealed class Service
{
    public object? Resolve(global::System.IServiceProvider provider) => provider.GetService(typeof(string));
}
```

```text
DD0003: 'System.IServiceProvider.GetService' resolves a service at run time, and this project is not a composition root.
Decide: take the dependency as a constructor parameter so the compiler can see it, or move this wiring into the composition root and set ArchCompositionRoot=true there | mark it [DesignDecision(typeof(<Set>.<Key>), Scope = ExceptionScope.<Scope>)] citing the accepted decision that says so.
Do not add the attribute without a decision that answers this; if the reason is only that the code already looked like this, take the design change.
```

## Conforming example

```csharp
internal sealed class Service
{
    private readonly IClock clock;

    public Service(IClock clock) => this.clock = clock;
}
```

The dependency is a parameter, so the compiler sees it and so does DD0001.
