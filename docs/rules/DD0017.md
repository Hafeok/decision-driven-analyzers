# DD0017: Close the hierarchy, or do not switch on it

|  |  |
| --- | --- |
| **Id** | `DD0017` |
| **Tier** | 2 (warning, heuristic, written false-positive story) |
| **Severity** | warning |
| **Motivating decision** | `Hierarchies.TypeSwitchOverOpenHierarchyWarning` |
| **Introduced in** | unreleased |

## Principle

A switch over subtypes is a claim that the list is complete. Something has to be making that claim
true, and "nobody has added one yet" is not it.

## What the rule checks

A `switch` statement or `switch` expression whose arms test **two or more** subtypes of a common
base class, where nothing closes that base.

One arm testing a type is a type test, not a claim about a set, and is not reported.

**Closed** means one of:

- a `private` constructor on the base — only nested types can call one, and they are in the same
  file;
- a `file`-local base;
- a base no one outside the assembly can derive from — an `internal` or `private protected`
  constructor, or an `internal` base whatever its constructor says — **and** every derived type in
  the compilation is `sealed`.

Anything else is open. A base with a `public` or `protected` constructor is open by definition: the
next subtype may be in somebody else's assembly, and this compilation will never see it.

Interfaces are not considered. An interface is open by construction, so treating one as a hierarchy
would make the rule read "do not switch on interfaces", which is not what it means.

**Framework hierarchies are excluded by default.** `Exception`, `Stream` and their relatives are
open by design, always will be, and a consumer cannot close them. A warning nobody can act on is a
warning people learn to skip — including past the ones that matter.

### The discard arm

`_ => throw new ArgumentOutOfRangeException(...)` **still warns**, and this is the part worth
reading twice, because it looks like the defence and is the defect.

A throwing discard arm moves the failure from compile time to run time. With a closed hierarchy,
adding a subtype breaks the build in front of the person adding it, with the file and line of every
switch that needs updating. With an open one and a throwing default, it compiles, ships, and throws
in front of a user — and the stack trace names the switch rather than the subtype nobody handled.

The exhaustive-switch warning the compiler gives you on a closed hierarchy is the thing being asked
for. A discard arm suppresses that too.

## False-positive story

This rule is a heuristic. "Closed" is a judgement about types that do not exist yet, and the rule
can only see the ones that do. Four cases where it will be wrong:

**A hierarchy closed by convention rather than by the compiler.** A base with a `public` constructor
that everyone knows not to derive from. The rule reports it, and it is right to: the convention is
not checked by anything, which is the whole premise of this repository.

**A switch that is deliberately partial.** Handling two interesting subtypes and treating the rest
uniformly is a legitimate shape — a renderer with a fast path for two node kinds. The rule reports
it. The honest answers are to make the uniform case a virtual member on the base, or to cite a
decision saying the partial switch is intended.

**A base outside your control that is not the framework's.** A third-party hierarchy is open, you
cannot close it, and the default framework exclusion does not cover it. `[DesignDecision(..., Scope
= ExceptionScope.Interop)]` is the answer, and it leaves a citation naming which foreign hierarchy
is being switched on.

**Generic bases.** The rule compares original definitions, so `Node<int>` and `Node<string>` are one
base. That is usually what is meant and occasionally is not.

Where the rule is right, it is right about a defect with no other detector: the next subtype gets
whatever the last arm does, and nothing anywhere says that was a decision.

**Promotion.** `RuleTiers.Tier2PromotionBySupersession`: tier 1 only by a superseding decision,
after running on a real codebase without false positives. The partial-switch case above makes that
unlikely.

## Applying the fixes

`dotnet build` never runs a code fix, so a fix that only an IDE can reach is invisible to anyone
working from a terminal — an agent included. From a terminal:

```
dotnet format analyzers --diagnostics DD0017
```

No fix is registered. Closing a hierarchy changes the base's constructor and every leaf's
declaration, and replacing the switch with a virtual member moves code into each subtype — both are
the design work the warning is asking for.

## Violating example

```csharp
public abstract class Node { }
public sealed class Add : Node { }
public sealed class Mul : Node { }

public static class Eval
{
    public static int Of(Node n) => n switch
    {
        Add => 1,
        Mul => 2,
        _ => throw new ArgumentOutOfRangeException(nameof(n)),
    };
}
```

```text
DD0017: this switch tests 2 subtypes of 'Consumer.Node', and nothing closes 'Consumer.Node'.
Decide: close the hierarchy - give 'Consumer.Node' a private or file constructor and seal its leaves, so the compiler checks the switch is exhaustive - or replace the switch with a virtual member on the base | mark it [DesignDecision(typeof(<Set>.<Key>), Scope = ExceptionScope.<Scope>)] citing the accepted decision that says so.
Do not add the attribute without a decision that answers this; if the reason is only that the code already looked like this, take the design change.
```

## Conforming example

```csharp
public abstract class Node
{
    private Node() { }

    public sealed class Add : Node { }
    public sealed class Mul : Node { }
}

public static class Eval
{
    public static int Of(Node n) => n switch
    {
        Node.Add => 1,
        Node.Mul => 2,
    };
}
```

No discard arm, because there is nothing left to discard. Adding `Node.Div` breaks this build, in
this file, in front of whoever added it.
