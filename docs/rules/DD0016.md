# DD0016: Prefer an enum to a flag argument

|  |  |
| --- | --- |
| **Id** | `DD0016` |
| **Tier** | 2 (warning, heuristic, written false-positive story) |
| **Severity** | warning |
| **Motivating decision** | `PrimitiveFreeSurfaces.FlagArgumentsWarning` |
| **Introduced in** | 0.1.0-preview.1 |

## Principle

`Find(id, true)` says nothing at the call site. The parameter name is in the declaration, the value
is in the call, and the reader has to hold one while looking at the other.

## What the rule checks

A `bool` parameter on a `[Contract]` member, or on a public member of a type in a `[DomainModel]`
namespace.

Three things are not reported, and they are what separate a flag from a `bool` that is doing honest
work:

- **`out bool` and `ref bool`.** `TryParse(s, out bool value)` returns its answer through the
  parameter; nothing is being switched.
- **A delegate returning `bool`.** `Func<T, bool>` is a predicate, and the `bool` is its result.
- **A `bool` return type.** A member that answers a yes-or-no question is answering it.

| Setting | Where | Default | Effect |

## False-positive story

*Written before the analyzer, as a tier-2 rule requires (`RuleTiers.ThreeTiers`). This section is
the claim being tested by running the rule, not a report of how it went.*

This rule is a heuristic. It reads a type, and what it is trying to see is a call site it cannot
reach. Three cases where it will be wrong:

**A `bool` that is genuinely the data.** `SetVisible(bool visible)`, `Configure(bool enabled)` — a
member whose entire subject is a two-state fact, where the parameter name and the member name say
the same word. The rule reports these and the enum would be ceremony:
`SetVisible(Visibility.Visible)` reads worse than what it replaced. This is the most common false
positive and the reason the rule is tier 2 rather than tier 1.

**Implementing somebody else's interface.** A `bool` parameter inherited from a framework or
third-party interface cannot be changed without breaking the implementation. The answer is
`[DesignDecision(..., Scope = ExceptionScope.Compatibility)]`, and the rule is right that a decision
was made — just not by whoever is reading the warning.

**A builder or options shape.** `WithCaching(bool)` in a fluent chain is read next to its own name
at the call site, which is the thing the rule is worried about and cannot see.

Where the rule is right, it is right about something worth the noise: a second `bool` parameter is
almost always a real defect, because at that point the call site is `Find(id, true, false)` and the
two are silently swappable in exactly the way DD0013 exists to prevent.

**What is not an answer.** `#pragma warning disable DD0016` is DD0008. The answers are: change the
parameter to an enum, split the member in two, or mark it `[DesignDecision]` citing the decision
that says the `bool` is right here.

**Promotion.** `RuleTiers.Tier2PromotionBySupersession`: this becomes tier 1 only by a superseding
decision, after running on a real codebase without false positives. Given the first case above, that
is not expected.

## Applying the fixes

`dotnet build` never runs a code fix, so a fix that only an IDE can reach is invisible to anyone
working from a terminal — an agent included. From a terminal:

```
dotnet format analyzers --diagnostics DD0016
```

No fix is registered. Replacing a `bool` parameter with an enum means naming the enum and its two
members, which is the design work the warning is asking for; a generated `Flag.True` / `Flag.False`
would satisfy the rule and change nothing.

## Violating example

```csharp
namespace Consumer
{
    [Contract(typeof(CatalogShape.ProductLookupContract), Role = "catalog read side")]
    public interface IProductLookup
    {
        Product? Find(ProductId id, bool includeArchived);
    }
}
```

```text
DD0016: parameter 'includeArchived' of 'IProductLookup.Find' is a bool, so the call site reads 'Find(x, true)'.
Decide: give it an enum with two named members, or split the member in two | mark it [DesignDecision(typeof(<Set>.<Key>), Scope = ExceptionScope.<Scope>)] citing the accepted decision that says so.
Do not add the attribute without a decision that answers this; if the reason is only that the code already looked like this, take the design change.
```

## Conforming example

```csharp
namespace Consumer
{
    public enum ArchivedProducts { Excluded, Included }

    [Contract(typeof(CatalogShape.ProductLookupContract), Role = "catalog read side")]
    public interface IProductLookup
    {
        Product? Find(ProductId id, ArchivedProducts archived);
    }
}
```

`Find(id, ArchivedProducts.Included)` says at the call site what `Find(id, true)` said only in the
declaration.
