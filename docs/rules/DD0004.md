# DD0004: Do not hold mutable static state

|  |  |
| --- | --- |
| **Id** | `DD0004` |
| **Tier** | 1 (error, mechanical, single compilation) |
| **Severity** | error |
| **Motivating decision** | `StaticState.NoMutableStaticState` |
| **Introduced in** | 0.1.0-alpha.0.21 |

## Principle

A mutable static is shared by every caller on every thread. A static *collection* is worse: it is
how a lower layer discovers a higher one without a reference, which is the hole a layering rule
cannot see.

## What the rule checks

| Shape | Result |
| --- | --- |
| `const` | conforms |
| `static readonly` of an immutable type | conforms |
| `static` field that is not `readonly` | reported |
| `static readonly` field of a mutable type | reported |
| `static readonly` field of a collection type | reported, named as a registry |
| `static` property with a setter | reported |
| `[ThreadStatic]` field | reported |
| `AsyncLocal<T>` / `ThreadLocal<T>` static | reported |
| anything marked `[DesignDecision]` | conforms |

"Mutable" is a heuristic, because C# cannot be asked. A type is treated as mutable when it is an
array, a collection, `StringBuilder`, a `Lazy<T>` of a mutable type, or has a publicly settable
property or non-`readonly` public field. The bias is towards reporting: a static of a type that
turns out to be immutable costs a one-line exemption, and a static of a type that turns out not to
be is a defect nobody finds.

These are exempt by name, per ADR-A05, because each is famously shared on purpose: `Regex`,
`Encoding`, `ArrayPool<T>`, `MemoryPool<T>`, the `System.Collections.Immutable` and `Frozen`
collections, and the value types `DateTime`, `Guid`, `Uri`, `Version`, `Type` and their relatives.

### The registry

ADR-A05 describes registry detection as "a static field of a collection or delegate-list type
written from any member". This rule reports a static collection whether or not it finds a write,
and the message names it as a registry when the type is a collection.

That is a deliberate narrowing: a static collection nothing writes is still shared mutable state,
and the write can be added in the next commit without the rule noticing. Requiring the write would
mean the rule's answer depends on a member somewhere else in the compilation, which is the kind of
non-local judgement `RuleTiers.ThreeTiers` puts in the tier-3 report rather than in a gate.

## Configuration

None. The exemption is per member and is `[DesignDecision]`, not a setting —
`StaticState.PoolsExemptByDesignDecision`. An assembly-wide allow list was rejected in ADR-A05
because it hides the next static inside an already-exempt assembly.

Test assemblies (`*.Tests`) are not checked: a fixture holding shared state is a test concern, and
reporting it would push people towards suppressions in the one place the pattern is defensible.

## False-positive story

Tier 1, but the mutability heuristic is where it can be wrong. Two known shapes:

- **An immutable type the rule cannot recognise.** A hand-written value type with no setters is
  read correctly; one that exposes a mutable field for performance is not, and is reported. The
  answer is `[DesignDecision]` on the static, citing the decision that says the sharing is intended.
- **A lookup table that genuinely never changes.** `static readonly Dictionary<,>` is reported
  because `Dictionary` is mutable. The design change is real: use `FrozenDictionary` or
  `ImmutableDictionary`, and the rule goes quiet.

Suppression is not an answer (DD0008). Whether the cited decision exists and whether its scope is
right is DD0007's question, not this rule's — one rule, one judgement.

## Applying the fixes

`dotnet build` never runs a code fix, so a fix that only an IDE can reach is invisible to anyone
working from a terminal — an agent included. From a terminal:

```
dotnet format analyzers --diagnostics DD0004
```

The placeholder fix is not registered for this rule, so there is nothing to apply and the command
above reports no fixable diagnostics.

That is deliberate. The two answers — move the state onto an instance the caller owns, or declare it
a pool and cite the decision that introduced it — are the same edit to a tool and completely
different claims about the design. A fix that guessed between them would have to be reviewed line by
line, which is the work it was supposed to save.

## Violating example

```csharp
internal sealed class Registry
{
    private static readonly global::System.Collections.Generic.Dictionary<string, object> Handlers = new();

    public void Register(string key, object handler) => Handlers[key] = handler;
}
```

```text
DD0004: static readonly field 'Registry.Handlers' holds a mutable collection 'System.Collections.Generic.Dictionary<string, object>', which is the shape of a static registry.
Decide: make it an immutable collection if it never changes, or give the collection to the object that owns it and pass that object where it is needed | mark it [DesignDecision(typeof(<Set>.<Key>), Scope = ExceptionScope.<Scope>)] citing the accepted decision that says so.
Do not add the attribute without a decision that answers this; if the reason is only that the code already looked like this, take the design change.
```

## Conforming example

The state belongs to an object, and that object is passed where it is needed:

```csharp
internal sealed class Registry
{
    private readonly Dictionary<string, object> handlers = new();

    public void Register(string key, object handler) => handlers[key] = handler;
}
```

Or, for a pool, the exception is documented:

```csharp
[DesignDecision(typeof(StaticState.PoolsExemptByDesignDecision), Scope = ExceptionScope.Pool)]
private static readonly ArrayPool<byte> Buffers = ArrayPool<byte>.Shared;
```
