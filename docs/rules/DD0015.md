# DD0015: No implicit conversion between a model type and a primitive

|  |  |
| --- | --- |
| **Id** | `DD0015` |
| **Tier** | 1 (error, mechanical, single compilation) |
| **Severity** | error |
| **Motivating decision** | `PrimitiveFreeSurfaces.NoImplicitPrimitiveConversions` |
| **Introduced in** | 0.1.0-preview.1 |

## Principle

An implicit conversion puts the swappable argument back while leaving the signature looking like it
was fixed.

## What the rule checks

An `implicit operator` declared on a type in a `[DomainModel]` namespace, where either side is a
banned primitive (DD0013's list) — in either direction.

`explicit operator` is allowed. A named accessor such as `.Value` or `.AsLong()` is allowed. Both
cost a word at the call site, and the word is the point: it says which of the two things this is.

## Configuration

| Setting | Where | Default | Effect |
| --- | --- | --- | --- |
| `dd_banned_primitive_types_add` | `.editorconfig` | DD0013's list plus additions | What counts as the primitive. |
| `ArchLayer` | MSBuild property | none | The rule runs only when this is set. |

## False-positive story

Tier 1 and decidable: one operator declaration, one type list.

The case that looks like a false positive and is not: an implicit conversion added for ergonomics,
so that existing code passing a `long` keeps compiling during a migration. The rule is right that
this reintroduces the defect, and right that it is a decision — `[DesignDecision(..., Scope =
ExceptionScope.Migration)]` is what that scope is for, and it leaves a citation that the report tool
will list when somebody asks what is still mid-migration.

An implicit conversion between two *model* types is not reported. That is a different question and
this rule has no view on it.

## Applying the fixes

`dotnet build` never runs a code fix, so a fix that only an IDE can reach is invisible to anyone
working from a terminal — an agent included. From a terminal:

```
dotnet format analyzers --diagnostics DD0015
```

No fix is registered, although adding `explicit` would be mechanical. It is left off deliberately:
a one-keystroke fix here turns every call site into a compile error somewhere else, and the person
who accepted the lightbulb is not the person who will be reading those.

## Violating example

```csharp
namespace Consumer.Model
{
    public readonly record struct Position(long Value)
    {
        public static implicit operator long(Position p) => p.Value;
    }
}
```

```text
DD0015: 'Consumer.Model.Position' has an implicit conversion to 'long', so the primitive and the model type are interchangeable again.
Decide: make it 'explicit', or replace it with a named accessor such as '.Value' - both cost a word at the call site, which is the word that says which of the two this is | mark it [DesignDecision(typeof(<Set>.<Key>), Scope = ExceptionScope.<Scope>)] citing the accepted decision that says so.
Do not add the attribute without a decision that answers this; if the reason is only that the code already looked like this, take the design change.
```

## Conforming example

```csharp
namespace Consumer.Model
{
    public readonly record struct Position(long Value)
    {
        public static explicit operator long(Position p) => p.Value;
    }
}
```

`(long)position` at the call site, or `position.Value`. Either way the reader sees the moment the
type is taken off.
