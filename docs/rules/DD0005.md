# DD0005: Do not use a grab-bag name for an assembly or a namespace

|  |  |
| --- | --- |
| **Id** | `DD0005` |
| **Tier** | 1 (error, mechanical, single compilation) |
| **Severity** | error |
| **Motivating decision** | `NamesAndNamespaces.BannedGrabBagNames` |
| **Introduced in** | 0.1.0-alpha.0.21 |

## Principle

`Common`, `Core`, `Utils` and their relatives are where the second reason to change accumulates. A
package with one reason to change can be named after it.

## What the rule checks

No assembly name segment, and no namespace segment containing a public type, may be one of:

`Common` · `Core` · `Utils` · `Utilities` · `Helpers` · `Abstractions` · `Shared` · `Misc` ·
`Internal` · `Extensions`

Two distinctions the rule draws on purpose:

- **`Internal` is banned as a *public* namespace.** A namespace holding only internal types is an
  implementation detail, which is what `Internal` is there to say. Only public types make a
  namespace part of a package's shape, so only they are checked.
- **`Extensions` is banned as a namespace, not as a type name.** `StringExtensions` says what it
  extends. An `Extensions` namespace says only that somebody had nowhere else to put things.

ADR-A06's argument for a name rule rather than a cohesion metric is that the metrics are worse:
LCOM-family numbers are noisy, penalise span-based code by construction, and are the first thing
anybody suppresses. `NamesAndNamespaces.CohesionMetricsAreReport` sends them to the tier-3 report.

## Configuration

| Setting | Where | Default | Effect |
| --- | --- | --- | --- |
| `dd_banned_names` | `.editorconfig` | the list above | Replaces the list entirely, comma-separated |

Replacing rather than extending is deliberate: a consumer whose domain genuinely has a `Core` can
say so, and can ban something of its own instead. Setting it to an empty value turns the rule off,
which is a decision somebody is making visibly rather than a suppression.

## False-positive story

Tier 1 and decidable: it compares strings. The false positives it has are domain collisions —
a product whose subject matter really is called `Core`, or a `Shared` that names a real bounded
concept. `dd_banned_names` exists for exactly that, and using it is cheaper and more honest than a
per-type exemption.

The rule reports once per type, not once per banned segment, because a namespace with two of them
has one problem. An assembly whose name *and* namespace are both grab-bags produces two findings —
one rename fixes both, and neither is redundant: an assembly named `Sample.Common` whose types live
in `Sample.Ingest` produces only the first.

## Applying the fixes

`dotnet build` never runs a code fix, so a fix that only an IDE can reach is invisible to anyone
working from a terminal — an agent included. From a terminal:

```
dotnet format analyzers --diagnostics DD0005
```

No fix is registered. Renaming an assembly or a namespace is a change to every file that uses it and
to every consumer that references it; a code action that did it silently would be a refactor
disguised as a lightbulb.

The rename belongs in the IDE's own rename, or in the project file, where it is reviewable.

## Violating example

```csharp
namespace Sample.Layer1.Utils
{
    public sealed class Thing { }
}
```

```text
DD0005: public type 'Thing' is in namespace 'Sample.Layer1.Utils', whose segment 'Utils' is a grab-bag name.
Decide: name the namespace for what the types in it are responsible for, or move them into the namespace of the thing they belong to | mark it [DesignDecision(typeof(<Set>.<Key>), Scope = ExceptionScope.<Scope>)] citing the accepted decision that says so.
Do not add the attribute without a decision that answers this; if the reason is only that the code already looked like this, take the design change.
```

## Conforming example

```csharp
namespace Sample.Layer1.Ingest
{
    public sealed class Reader { }
}
```
