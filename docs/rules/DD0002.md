# DD0002: Do not grant InternalsVisibleTo to anything but a test assembly

|  |  |
| --- | --- |
| **Id** | `DD0002` |
| **Tier** | 1 (error, mechanical, single compilation) |
| **Severity** | error |
| **Motivating decision** | `StableDependencyRules.InternalsVisibleToTestsOnly` |
| **Introduced in** | unreleased |

## Principle

A dependency that the reference graph does not show is a dependency nobody can reason about.
`InternalsVisibleTo` creates exactly that, and tests are the one place where reaching inside is the
point rather than a shortcut.

## What the rule checks

Every `[assembly: InternalsVisibleTo(...)]` on the compilation must name an assembly whose simple
name ends `.Tests`.

The simple name is taken from before the first comma, because a signed grant carries the public key
after one: `"Sample.Layer1.Tests, PublicKey=0024…"`. Matching the whole string would report every
signed grant, including the legitimate ones.

The diagnostic points at the attribute where it is in source, rather than at the project, because
the grant is a line somebody wrote.

## Configuration

None. The rule needs nothing configured and runs in every project, which is why it is also the
cheapest of the three to adopt.

## False-positive story

Tier 1 and decidable: the rule reads a string argument that is in the compilation. It has one edge:
a grant that arrives from a generated file or another compilation has no syntax to point at, and is
reported without a caret. The finding is still right.

`.Tests` is a suffix on the assembly name, not a project naming convention, so a test project whose
assembly is named something else is reported. That is the rule working: the exemption exists for
assemblies that are visibly tests.

## Applying the fixes

`dotnet build` never runs a code fix, so a fix that only an IDE can reach is invisible to anyone
working from a terminal — an agent included. From a terminal:

```
dotnet format analyzers --diagnostics DD0002
```

Two fixes are offered on a grant: remove it, which is the design change and is mechanical because
the grant is one line that means one thing; or the documented-exception placeholder.

Neither offers fix-all. Removing every grant at once breaks all the code that relied on them
together, with nothing to read but a wall of errors; one at a time, each removal shows which code
was reaching inside and why.

The documented-exception fix inserts `[DesignDecision(typeof(____.____), Scope = ExceptionScope.____)]`,
which does not compile (`DiagnosticMessages.PlaceholderFixDoesNotCompile`). That is the point: the
build stays red with one remaining error naming exactly what is missing, and no fix reaches green
without either a design change or a filed, accepted decision.

## Violating example

```csharp
[assembly: System.Runtime.CompilerServices.InternalsVisibleTo("Sample.Layer2")]
```

```text
DD0002: 'Sample.Layer1' grants InternalsVisibleTo to 'Sample.Layer2', which is not a test assembly.
Decide: drop the grant and use the public surface, or move the code that needs the internals into 'Sample.Layer1' or into a '*.Tests' assembly | mark it [DesignDecision(typeof(<Set>.<Key>), Scope = ExceptionScope.<Scope>)] citing the accepted decision that says so.
Do not add the attribute without a decision that answers this; if the reason is only that the code already looked like this, take the design change.
```

## Conforming example

```csharp
[assembly: System.Runtime.CompilerServices.InternalsVisibleTo("Sample.Layer1.Tests")]
```
